# V1

## Goal

Ship a serious personal daily-driver for a narrow workflow with the core architecture in place.

## Why this version exists

V1 exists to make `opencode-modded-rust` useful in real daily practice as early as possible without collapsing into a broad parity chase.

## Scope

- TUI is the main interface.
- Local model execution works end-to-end.
- The runtime uses explicit task stages instead of an unconstrained chat loop.
- Structured task state exists outside conversation history.
- Implementation and review are separate stages.
- Verification is required before task completion.

## Narrow workflow

- inspect a local repository
- define or select one bounded coding task
- build focused working context for that task
- edit code and related files
- run local verification relevant to the task
- perform fresh-context review
- either accept the task result or reopen it for repair

## Required capabilities

- a usable TUI workflow for the core agent loop
- local model provider integration sufficient for daily use
- explicit task stages owned by the runtime
- durable task state outside transcript history
- focused context construction for a bounded task
- file editing, repository reads, and shell execution
- verification and review as separate stages
- session continuity across active work
- a stable task-state core that a decision provider can call without becoming
  part of the core
- an engine-neutral decision boundary that can host Jev/Laya as advisory
  System-1 policy, with deterministic rules and human gates still authoritative

## Explicit non-goals

- full OpenCode feature parity
- desktop app support
- MCP
- broad plugin or ecosystem completeness
- broad distribution and packaging goals
- wide autonomous multi-project execution

## What is still missing from V1

- broader workflow coverage beyond the narrow daily-driver loop
- mature structural retrieval through `ScopeMux`
- selective adoption of higher-value reference features beyond the frozen baseline
- richer task-graphing and cross-task orchestration
- expanded ergonomics and non-core surfaces
- full System-1 decision coverage (V1 requires the boundary and the first advisory
  classes, not every decision class)

## Success gate

V1 succeeds when the system is good enough to use personally for real coding work within a narrow, intentionally bounded workflow.

## Dependencies

- the current invariants remain authoritative even where V1 only partially realizes them
- deferred capabilities should become explicit later-version work rather than silently expanding V1
